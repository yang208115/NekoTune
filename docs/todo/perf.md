## 详细说明

### 10.1 QML 模块化与编译期检查 — P2 · M–L

- 现状：`frontend/qt-qml/CMakeLists.txt` 以 `resources.qrc` 打包 QML，`src/main.cpp` 通过 `setContextProperty` 注入 `i18n`、控制器等全局对象；qmlcachegen／qmlsc 不生效，qmllint 无法解析全局名称，绑定只能运行时解释。
- 方案：迁移到 `qt_add_qml_module`，控制器改为 `QML_SINGLETON` 或 required property；CI 增加 `all_qmllint`。
- 注意：迁移会改变 `AGENT.md` 中“新增 QML 同步 `resources.qrc`”的约定，需同步文档。

### 10.2 曲库多选与列表模型性能 — P2 · S–M

- `qml/components/LibraryPanel.qml:52-54`、`:323`、`:330`：每行执行 `selectedSongIds.indexOf`，全选判断为 `every` 套 `indexOf`，选择变化时全部行重算；每行还通过 `songActions(modelData)` 新建菜单数组。改为 C++ 侧 `QSet` 维护选择并以 role 或方法暴露，全选状态由控制器计算，菜单在打开时生成。
- `src/models/record_model.cpp:12-22`（已复核）：常规增量更新接近 O(n)，整体重排（如切换排序）退化为 O(n²)，且每次比较都 `toMap()` 复制。可先建标识到行号的索引，并缓存标识值。
- 验收：数千首曲库切换排序、全选、批量选择不卡顿；用 `QAbstractItemModelTester` 覆盖 `RecordModel` 增删改移。

10.7 宿主封面与缩略图解码尺寸统一已于 2026-10-28 完成并从清单移除，实现及验证范围见[验收记录](acceptance.md#2026-10-28-图片解码尺寸统一)。外部主题自带 QML 需单独适配，不以宿主更新视为主题包已更新。

### 10.8 扩展管理窗口与恢复引擎延迟创建 — P1 · S–M

- 已复核：`frontend/qt-qml/src/main.cpp` 启动即创建第二个 `QQmlApplicationEngine recoveryEngine` 并加载 `ExtensionsWindow.qml`；窗口未显示时，扩展管理页面对象也已创建。
- 方案：首次打开扩展管理时再创建引擎与窗口，此后按明确的复用／关闭策略管理；保持独立于扩展主题的恢复入口，不通过合并引擎破坏隔离。
- 验收：未打开管理窗口的启动阶段不实例化该窗口及页面；快捷键与菜单首次打开、反复打开、主题加载失败后的恢复和退出清理均正常。分别记录启动基线和首次打开后的内存，收益待实测。

### 10.9 图片尺寸档位、缓存与隐藏资源生命周期 — P2 · M

- 方案：在 10.7 的解码上限基础上，为缩略图归并合理尺寸档位，避免细微布局变化反复解码或生成多种缓存；覆盖 DPR 变化。按用途保留可复用小图缓存，对大图和已卸载视图释放像素／纹理；不要统一设置 `cache: false` 导致重复解码。
- 先复核缓存及资源实际持有者，再处理隐藏资源；保持页面草稿、滚动位置和返回速度，避免与 10.3 的离页保留状态冲突。字体缓存的上下文与数量增长也纳入观察，不以清空所有缓存作为默认策略。
- 验收：反复缩放、跨 DPR、滚动图片列表、隐藏／恢复背景、切歌和往返页面后，图片尺寸种类及资源数量趋于稳定；记录 CPU 解码、视觉清晰度、匿名内存与 GPU 资源变化，兼顾内存和响应速度。

### 10.10 曲库派生模型与临时分配优化 — P2 · M

- 已复核：`src/controllers/library_controller.cpp` 连接后请求完整曲库，`filter()` 构建排序／筛选列表及专辑聚合；首页也通过 `songs.items` 在 JS 中筛选和排序。10.3 延迟页面创建不等于延迟这些数据工作。
- 方案：先量化持有量和临时分配，评估筛选／排序改用代理模型或稳定 ID／索引，专辑等派生数据按消费需求构建；首页近期列表可由有界查询／模型提供。保留首页播放与曲库筛选的独立语义，不直接停掉首页依赖的曲库请求。
- Qt 容器可能隐式共享，不能将 `QVariantList` 按值返回直接当作深拷贝证据；避免未经测量重构全部数据层。本项聚焦内存，10.2 继续负责列表更新复杂度与多选性能。
- 验收：用同一份数千首曲库测量启动、首次进入曲库／专辑、筛选与排序后的内存和临时分配；增删改同步、自然排序、全选、播放顺序与稳定歌曲身份保持正确。

### 10.11 Starcape 自定义 Shell 页面按需加载 — P1 · S–M

- 已复核：本机安装的 Starcape 1.1.2 自带 `qml/Shell.qml` 与 `qml/shell/PageHost.qml`，通过 Repeater 创建页面，`Component.onCompleted` 立即调用 `loadNative()`，隐藏页面仍加载。宿主 10.3 的完成范围是默认 Shell，不能视为已覆盖外部主题自定义 Shell。
- 方案：在 `NekoTune-extensions/extensions/starcape` 对应独立仓库复核当前源码并同步首次访问激活机制，同时将主题自带封面及占位图的解码尺寸约束与宿主 10.7 对齐；发布／更新主题包后再验证，不能仅改宿主或只改用户安装目录便声称完成。
- 验收：自定义 Shell 启动仅实例化需要的页面，首次访问后保留草稿／滚动等状态；隐藏页面显式操作、动态扩展页面、诊断页开关和新建歌单行为与宿主约定一致。默认界面及 Starcape 分别采样，不混算收益。

### 10.12 malloc 空闲保留与长期内存稳定性 — P2 · M

- 现象：启动现场 arena 空闲约 27.55 MiB，长期现场约 228.67 MiB；空闲地址空间不等于驻留量，也不等于可直接归还的内存。现有音频环形缓冲优化保留，不据此重新认定 PCM 为主因。
- 方案：先完成 10.7–10.10 对大块分配和生命周期的优化，再在隔离运行中比较 arena 在用／空闲、实际驻留及回收效果；必要时评估大块分配策略、arena 数量或空闲阶段的回收。不要未经验证定时 `malloc_trim`、强制清缓存或替换分配器。
- 验收：统一操作序列执行启动、页面往返、长时间播放、反复切歌及资源释放，区分有界缓存与持续增长；记录内存趋势、卡顿／CPU、音频稳定性和平台差异。Linux 分配器实验不直接推断 Windows 收益。

## 内存分析与共同验收基线（2026-10-28）

- Linux、Qt 6.11.2，本地构建 `CMAKE_BUILD_TYPE` 为空。PID 273174 的默认主题启动观察值为 RSS 420.30 MiB、匿名内存 171.41 MiB、PSS 260.14 MiB；后续驻留页快照量级稳定。字体文件映射 RSS 约 64 MiB，图形库 Mesa／LLVM 映射约 51 MiB，其中包含可共享／可回收的文件页，不能全视为独占业务内存。
- 驻留页快照中，arena 在用约 93.44 MiB、空闲约 27.55 MiB，另识别 malloc mmap 块约 24.87 MiB；已确认图片像素约 35.07 MiB、字体距离场约 4.81 MiB。图片／距离场是 malloc 分配的子集，不能把这些数值相加；未获得分配出生栈，不能将剩余在用量全部归给曲库或 UI。
- 长期现场 PID 52099 抓取前 RSS 约 770 MiB、匿名内存约 518 MiB，两路 PCM 各 3 MiB；同类近全零大块在本次现场定位为字体距离场缓存约 36 MiB。不能以此追溯确认 10 月 25 日未保存现场的所有未知块，也不能仅凭单次快照认定泄漏。
- 本地原始证据与报告位于忽略目录 `build/memory-default-273174/`、`build/memory-20261028-1555/`，不随仓库交付。前者只复制已驻留的可写页，非完整调试 core；后者 gcore 存在与所分析 arena 不重叠的读取失败区段，且读取文件／GPU 映射后影响了 RSS，因此采用抓取前统计。
- 共同验收：记录实际运行的构建、有效主题／布局、窗口／壁纸状态、DPR、同一曲库及相同操作序列，分别测启动、首次访问全部页面、反复操作和空闲释放后的 RSS、PSS、匿名内存及图片／字体缓存数量。采样方式前后一致，记录暂停及缺页影响；区分当前占用、峰值和长期增长，不承诺固定节省量。
